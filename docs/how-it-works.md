# Как работает получение Root

Техническое объяснение для новичков.

Здесь описана схема lite-kit. Также разобран наш эксперимент.

Это не исходный код проекта. Это объяснение основных процессов.

---

## Общая схема

Станция обращается к сервисам Яндекса. Запросы проходят через домашний роутер.

Мы меняем DNS-направление. Нужные домены ведут на компьютер.

Компьютер запускает локальный стенд. Стенд отвечает на запросы станции.

Он также отдаёт прошивку. Затем изменяет ответ синхронизации.

В результате включается сетевой ADB. На нашей модели shell оказался root.

---

## 1. Что делает DNS

В проекте используется dnsmasq. Он принимает DNS-запросы локально.

Основные домены перенаправляются:

```text
quasar.yandex.net
quasar.yandex.ru
scbh.yandex.net
```

Они возвращают адрес компьютера. Так запрос попадает в стенд.

Остальные домены идут дальше. Для них настроены DNS-пересылки.

### Зачем фильтруются AAAA

Записи AAAA содержат IPv6-адреса. Станция могла обойти локальный стенд.

Поэтому шаблон использует `filter-AAAA`. Это блокирует обход через IPv6.

### Особые поддомены

Поддомены `iot.quasar` исключены. Они отправляются на внешний DNS.

Это сделано настройками dnsmasq. Не меняйте их без понимания.

---

## 2. Что делает HTTPS-сервер

Локальный сервер использует eQuasar. Он принимает HTTP и HTTPS.

Используются порты 80 и 443. DNS работает на порту 53.

Сервер использует сертификаты проекта. Они находятся в каталоге `certs`.

Не заменяйте их случайными файлами. Не публикуйте приватные ключи.

Сервер различает запросы станции. Запросы телефона идут иначе.

Так приложение продолжает работать. Подмена ограничивается самой колонкой.

---

## 3. Как выбирается прошивка

Колонка отправляет `check_updates`. В запросе есть версия и платформа.

Например, платформа `yandexmini_2`. Версия указывается отдельно.

Сервер ищет папку платформы. Для нашей модели это:

```text
firmware/yandexmini_2/
```

Внутри лежит ZIP-файл. Рядом лежит `manifest.json`.

Сервер сверяет платформу прошивки. Чужую платформу он не выдаёт.

Затем сравнивается версия колонки. Если версии различаются, появляется OTA.

Если версии уже совпадают, сервер отвечает `hasUpdate:false`.

### Защитный маркер

Файл `run/no_downgrade` блокирует OTA. Он служит аварийным выключателем.

Пока файл существует, сервер не предлагает обновление.

После теста блокировку нужно вернуть. Так случайная выдача будет отключена.

### Что находится в OTA-ответе

Сервер формирует JSON-манифест. В нём указана целевая версия.

Также указывается URL загрузки. Добавляется контрольная сумма CRC32.

Есть резервный URL. Есть адрес локального компьютера.

Колонка использует эти параметры. Затем скачивает сам архив.

---

## 4. Как передаётся архив

Колонка обращается к OTA-адресу. Сервер находит нужный ZIP.

Передача поддерживает HTTP Range. Это позволяет загружать части файла.

В журнале виден размер. Также видны границы переданных байтов.

Для полного файла появляется:

```text
[OTA] файл отдан ПОЛНОСТЬЮ
```

В нашем тесте передано:

```text
67796480 байт
```

Это подтверждает полную отдачу. Но не заменяет проверку прошивки.

После установки меняется версия. Колонка снова запрашивает обновления.

Сервер видит совпадение версий. Он отвечает `hasUpdate:false`.

---

## 5. Как включается ADB

После обновления станция синхронизируется. Она запрашивает `/get_sync_info`.

Сервер получает ответ Яндекса. В нашем тесте это был JSON.

Исходный ответ сохранял настройки модели. Сервер добавлял параметры ADB.

Основной блок выглядит так:

```json
{
  "remoteActivation": true,
  "network": true,
  "fullDurationMs": 31536000000
}
```

Эти параметры добавляются в несколько веток. Так повышается совместимость прошивок.

Добавление выполняется в:

- `config.system_config.adbd`;
- `config.device_config.adbd`;
- `config.adbd`;
- верхний `adbd`.

Сервер сохраняет остальные поля. Он не заменяет весь ответ шаблоном.

### Настоящий ответ или шаблон

Основной режим использует ответ Яндекса. Сервер добавляет в него ADB.

Если Яндекс отвечает ошибкой, сервер может использовать локальный шаблон.

При 429 и 5xx выполняются повторы. По умолчанию их три.

Между попытками есть пауза. Она составляет 2,5 секунды.

### Что увидели именно мы

В исходном ответе ADB отсутствовал. Это показала строка `SYNC-NATIVE`.

После обработки параметры появились. Это показала строка `SYNC-REAL→`.

Таким образом, сервер добавил ADB. Это подтверждено нашим журналом.

---

## 6. Почему появился Root

ADB и Root — разные вещи. ADB предоставляет удалённую командную оболочку.

Root определяет права этой оболочки. Это проверяется командой `id`.

На нашей станции результат был:

```text
uid=0(root) gid=0(root)
```

Это подтверждает root-пользователя. Но механизм запуска пока не исследован.

Мы не анализировали init полностью. Мы не меняли системные разделы.

Мы не устанавливали постоянные скрипты. Мы не проверяли загрузку после перезагрузки.

Поэтому постоянный Root не подтверждён. Подтверждён только проверенный сеанс.

## 7. Какие журналы смотреть

Основной журнал:

```text
log/server.log
```

Там видны запросы станции. Также видны ответы сервера.

Журнал Яндекса:

```text
log/yandex.log
```

Там видны внешние запросы. Содержимое секретов маскируется выборочно.

Локальный журнал:

```text
log/local.log
```

Там видны локальные ответы. Например, OTA и Sync fallback.

DNS-журнал сервера:

```text
log/dns.log
```

Журнал dnsmasq:

```text
log/dnsmasq.log
```

Там видны DNS-запросы клиентов. Их можно использовать для диагностики.

### Чего нельзя публиковать

Не включайте `DUMP_SYNC=1`. Он сохраняет сырой ответ станции.

Не публикуйте `sync_real.json`. Внутри могут находиться секреты.

Не публикуйте полные заголовки. Там могут быть токены авторизации.

---

## 8. Что не является Root

Открытый порт не доказывает Root. Подключение ADB тоже недостаточно.

Команда `adb devices` показывает подключение. Она не показывает права пользователя.

Главная проверка — команда `id`. В нашем случае нужен `uid=0`.

Другой UID не подтверждает Root.

# Диагностика lite-kit

Пошаговая проверка ошибок.

Сначала определите этап сбоя. Не меняйте настройки наугад.

---

## 1. Стенд не запускается

Запустите стенд вручную.

```bash
cd ~/lite-kit
sudo ./start.sh
```

Посмотрите первые сообщения. Найдите первую ошибку.

Проверьте занятые порты.

```bash
sudo ss -lntup | grep -E ':(53|80|443)\\b'
```

Нужны свободные порты. DNS использует порт 53. HTTP использует порт 80. HTTPS использует порт 443.

### Ошибка Address already in use

Эта ошибка означает конфликт. Порт уже занят процессом.

Посмотрите владельца порта. Затем решите конфликт осознанно.

В нашем тесте мешали службы. Они занимали порты 80 и 443.

Не останавливайте всё подряд. Особенно осторожно с системными службами.

---

## 2. DNS не отвечает

Сначала проверьте IP компьютера.

```bash
ip -4 addr
```

Затем проверьте маршрут.

```bash
ip route
```

Убедитесь в правильном интерфейсе. Не используйте VPN-адрес.

Проверьте состояние dnsmasq.

```bash
pgrep -a dnsmasq
```

Проверьте его журнал.

```bash
tail -n 100 ~/lite-kit/log/dnsmasq.log
```

Проверьте локальный DNS.

```bash
dig +short @<IP_КОМПЬЮТЕРА> quasar.yandex.net A
```

Ожидается адрес компьютера. Не адрес внешнего сервера.

Проверьте остальные домены.

```bash
dig +short @<IP_КОМПЬЮТЕРА> quasar.yandex.ru A
dig +short @<IP_КОМПЬЮТЕРА> scbh.yandex.net A
```

Если ответы неправильные, остановитесь. Сначала исправьте DNS.

---

## 3. Внешние DNS недоступны

В стандартном шаблоне используются пересылки. Обычно это публичные DNS-серверы.

В нашем окружении были ограничения. Мы использовали AdGuard DNS.

Это была локальная адаптация. Она не обязательна для метода.

Откройте конфигурацию dnsmasq.

```bash
nano ~/lite-kit/config/dnsmasq.conf.tpl
```

В нашем варианте использовались строки:

```ini
server=94.140.14.14#53
server=94.140.15.15#53
#server=77.88.8.8
server=/iot.quasar.yandex.net/94.140.14.14
```

Не меняйте всё без проверки. Оставьте рабочие правила проекта.

Сохраните файл и перезапустите стенд.

```bash
cd ~/lite-kit
./stop.sh
sudo ./start.sh
```

Снова проверьте DNS-запросы.

---

## 4. Колонка не получает интернет

Сначала проверьте DHCP.

У колонки должен быть обычный IP. Адрес `169.254.x.x` недопустим.

Такой адрес означает проблему DHCP. Роутер не выдал нормальную аренду.

Проверьте список клиентов роутера. Проверьте старые DHCP-резервации.

Проверьте изоляцию Wi-Fi клиентов. Проверьте наличие второго DHCP-сервера.

Затем проверьте DNS роутера. Он должен указывать на компьютер.

Обновите подключение колонки. После этого проверьте журнал.

### Проверка generate_204

Станция проверяет доступность сети. Она обращается к `/generate_204`.

В норме сервер отвечает кодом 204. Это видно в журнале.

Ищите строки `HEAD /generate_204`. Проверьте код ответа.

---

## 5. Не появляется OTA-AUTO

Проверьте наличие архива.

```bash
ls -lh ~/lite-kit/firmware/yandexmini_2/
```

Проверьте манифест.

```bash
cat ~/lite-kit/firmware/yandexmini_2/manifest.json
```

Платформа должна быть `yandexmini_2`. Версия должна совпадать с архивом.

Проверьте защитный маркер.

```bash
ls -l ~/lite-kit/run/no_downgrade
```

Если файл существует, OTA заблокирована. Это штатная защитная функция.

Для теста блокировка временно отключается. После обновления её возвращают.

Проверьте режим запуска.

```bash
ls -l ~/lite-kit/run/downgrade
```

Установщик рекомендует этот флаг. Затем требуется перезапуск стенда.

```bash
cd ~/lite-kit
touch run/downgrade
./stop.sh
sudo ./start.sh
```

### Проверьте запрос станции

Ищите `check_updates`. В запросе должна быть нужная платформа.

В нашем случае это `yandexmini_2`. Версия должна отличаться от целевой.

---

## 6. Сообщение «прошивки нет»

Проверьте путь архива.

Он должен быть таким:

```text
firmware/yandexmini_2/<версия>.zip
```

Не кладите архив в случайную папку. Не меняйте имя файла.

### Важное замечание о сообщении

Иногда сервер пишет предупреждение. Например, `в firmware/ нет .zip`.

Это сообщение проверяет старую раскладку. Она использует ZIP в корне.

Новая раскладка другая. Она хранит ZIP по платформам.

Поэтому само предупреждение не всегда означает отсутствие прошивки.

Проверьте запрос `OTA-AUTO`. Проверьте фактическую отдачу ZIP.

---

## 7. OTA не передаёт файл полностью

Следите за журналом.

```bash
tail -f ~/lite-kit/log/server.log
```

Ищите запрос OTA-файла. Проверьте итоговый размер.

В нашем тесте передано:

```text
67796480 байт
```

Ожидаемая строка:

```text
[OTA] файл отдан ПОЛНОСТЬЮ (67796480 б)
```

Если размер меньше, остановитесь. Не выключайте колонку принудительно.

Проверьте сетевое соединение. Проверьте доступность компьютера.

Проверьте контрольные суммы архива. Не используйте повреждённый ZIP.

---

## 8. Sync не включает ADB

Проверьте запрос `get_sync_info`. Он должен появиться после OTA.

Ищите `SYNC-NATIVE`. Это исходные поля Яндекса.

Затем ищите `SYNC-REAL→`. Это ответ после обработки.

Ищите отметки `adbd=on`. Если их нет, проверьте сервер.

Не включайте `DUMP_SYNC=1` ради диагностики. Этот режим сохраняет сырой ответ.

---

## 9. Порт 5555 закрыт

Сначала найдите IP колонки. Посмотрите список клиентов роутера.

Проверьте доступность порта.

```bash
nc -vz -w 5 <IP_КОЛОНКИ> 5555
```

Если порт закрыт, проверьте Sync. Проверьте завершение OTA.

Проверьте версию прошивки. Она должна быть целевой.

Подождите завершения настройки. Затем повторите проверку.

### Автоматический поиск

В проекте есть скрипт проверки.

```bash
cd ~/lite-kit
./check.sh
```

Он ищет станцию в подсети. Он проверяет порт 5555.

Скрипт сканирует сеть /24. Он использует известный MAC-префикс.

В другой подсети поиск может ошибиться. Тогда используйте список клиентов роутера.

---

## 10. ADB подключается без Root

Выполните проверку пользователя.

```bash
adb shell id
```

Root подтверждается значением `uid=0`. Другой UID не является Root.

Не используйте `adb root` вслепую. В production-сборках команда может отказать.

Не записывайте файлы в систему. Сначала выясните текущие права.

---

## 11. Яндекс отвечает 429

Код 429 означает ограничение запросов. В нашем тесте это встречалось.

Стенд выполняет повторы. По умолчанию выполняются три попытки.

Пауза между ними — 2,5 секунды. Затем используется локальный ответ.

Проверьте итоговую строку Sync. Если ответ доставлен, продолжайте наблюдение.

---

## 12. Сбор диагностики

В проекте есть диагностический скрипт.

```bash
cd ~/lite-kit
./diag.sh
```

Он собирает журналы и настройки. Также проверяет сеть и порты.

Архив создаётся в каталоге проекта. Его можно использовать для анализа.

**Не отправляйте архив вслепую.** Сначала проверьте его содержимое.

Внутри могут быть приватные данные. Маскирование не гарантирует полной очистки.

Удалите device_id и адреса. Удалите токены и cookies.

Никогда не отправляйте `sync_real.json`. Не публикуйте приватные ключи.

---

## 13. После диагностики

Когда проблема найдена, исправьте её. Затем повторите только нужный этап.

Не запускайте обновление многократно. Сначала проверьте состояние колонки.

После завершения восстановите DNS роутера. Верните защитный маркер OTA.

Остановите локальный стенд.

```bash
cd ~/lite-kit
./stop.sh
```

# Root на Яндекс Станции Мини 2

Подробная инструкция для новичков.

Проверена одна конкретная модель. Это Мини 2 без часов. Номер модели — **YNDX-00021**.

> **Результат нашего эксперимента** 
> - Платформа: `yandexmini_2`.
> - Исходная прошивка: `0.17.1.32.1145264292.20211203.factory-3.FACTORY.factory`.
> - Установленная прошивка: `0.369.1.46.4778262943.20261013.299`.
> - ADB: сетевой порт `5555`.
> - Проверка Root: `uid=0(root) gid=0(root)`.

**Важно:** проверялась только эта конфигурация. Другие модели не проверялись. Другие версии также неизвестны.

Сохранение Root после перезагрузки пока не проверялось отдельно.

## Что мы делаем

Сначала подготовим компьютер. На нём запустим локальный стенд.

Стенд принимает запросы колонки. Он работает через локальную сеть.

Затем подготовим нужную прошивку. Колонка получит её через OTA.

После обновления включим ADB. Это произойдёт через Sync-ответ.

Затем подключимся через ADB. Проверим права суперпользователя командой `id`.

### Простыми словами

**DNS** помогает находить серверы. Мы направим нужные запросы локально.

**OTA** означает обновление прошивки. Колонка скачает подготовленный файл.

**Sync** означает синхронизацию настроек. В ответ добавляется параметр ADB.

**ADB** — отладочный интерфейс Android. Здесь он работает через сеть.

**Root** означает права суперпользователя. Такие права подтверждает команда `id`.

### Схема подключения

```text
                Интернет
                   |
                Роутер
                   |
          Локальная сеть Wi-Fi
             /           \
            /             \
       Компьютер         Колонка
       Ubuntu            YNDX-00021
          |                  |
       lite-kit               |
          |                  |
       DNS + HTTPS <---------+
          |
       OTA-файл
          |
       Sync с ADB
          |
       Порт 5555
          |
       Root shell
```

Компьютер и колонка связаны. Они используют одну сеть.

Роутер выдаёт DNS компьютера. Остальные запросы идут дальше.

## Подготовка Ubuntu

Откройте терминал Ubuntu.

Сначала обновите список пакетов.

```bash
sudo apt update
```

Теперь установите необходимые программы.

```bash
sudo apt install -y git python3 dnsmasq dnsutils openssl curl adb netcat-openbsd
```

Дождитесь окончания установки.

Проверьте установленный Python.

```bash
python3 --version
```

Проверьте установленный ADB.

```bash
adb version
```

Проверьте DNS-утилиту.

```bash
dig -v
```

Проверьте версию OpenSSL.

```bash
python3 -c 'import ssl; print(ssl.OPENSSL_VERSION)'
```

Нужен OpenSSL версии 1.1.1. Более новая версия подходит.

### Проверка портов

Стенду нужны три порта.

- DNS использует порт 53.
- HTTP использует порт 80.
- HTTPS использует порт 443.

Проверим занятые порты.

```bash
sudo ss -lntup | grep -E ':(53|80|443)\\b'
```

Посмотрите найденные процессы.

Не останавливайте службы наугад. Сначала выясните их назначение.

Особенно часто занят порт 53. Его может занимать systemd-resolved.

Также могут мешать другие серверы. Например, nginx или Apache.

Если порты заняты, сначала решите этот конфликт.

### Что означает ошибка

Сообщение `Address already in use` означает занятый сетевой порт.

В нашем тесте встречалась такая ошибка. Заняты были порты 80 и 443.

Пока конфликт не устранён, стенд полностью не запустится.

## Определение IP компьютера

Компьютер должен иметь LAN-адрес. Колонка должна обращаться именно туда.

Посмотрите маршрут по умолчанию.

```bash
ip route
```

Найдите строку `default`.

В ней указан сетевой интерфейс. Например, `enp1s0` или `eth0`.

Теперь покажите IPv4-адреса.

```bash
ip -4 addr
```

Найдите адрес локальной сети.

Не используйте адрес VPN. Не используйте адрес Docker.

Не используйте публичный IP. Нужен адрес домашней сети.

### Пример

Допустим, компьютер имеет адрес:

```text
192.168.1.250
```

Это только пример адреса. У вас он будет другим.

Запишите свой LAN-адрес. Он понадобится в следующих командах.

### Закрепление адреса

Лучше закрепить адрес заранее. Используйте DHCP-резервацию роутера.

Так адрес останется постоянным. Стенд не потеряет привязку.

Не добавляйте второй IP без необходимости. Актуальный скрипт умеет выбрать адрес.

## Загрузка прошивки

Теперь подготовим нужный файл.

Перейдите в каталог проекта.

```bash
cd ~/lite-kit
```

Запустите установщик прошивки.

```bash
./install-firmware.sh -p yandexmini_2
```

Установщик покажет список версий. Выберите нужную версию вручную.

Нужная версия указана ниже.

```text
0.369.1.46.4778262943.20261013.299
```

Не копируйте номер пункта. Список может измениться позже.

Ориентируйтесь только на версию. Проверьте всю строку внимательно.

### Что делает установщик

Он обращается к зеркалу прошивок. Сначала скачивает метаданные версии.

Затем загружает архив обновления. Проверяет размер и формат файла.

Затем рассчитывает CRC32 и SHA256. Проверяет CRC32 по метаданным.

После этого создаёт манифест. В нём записываются параметры файла.

Архив сохраняется отдельно. Для каждой платформы своя папка.

Нужный путь выглядит так:

```text
firmware/yandexmini_2/0.369.1.46.4778262943.20261013.299.zip
```

Рядом создаётся файл `manifest.json`.

### Важная особенность

Зеркало иногда отдаёт обрезанный файл. Установщик умеет это обнаруживать.

При необходимости он пробует официальный URL. Затем снова проверяет архив.

Не используйте неполный файл. Не пытайтесь его устанавливать.

## Проверка прошивки

Проверим созданные файлы.

Оставайтесь в каталоге проекта.

```bash
cd ~/lite-kit
```

Посмотрите содержимое папки.

```bash
ls -lh firmware/yandexmini_2/
```

Проверьте размер архива.

```bash
stat -c '%n — %s байт' firmware/yandexmini_2/0.369.1.46.4778262943.20261013.299.zip
```

В нашем тесте размер составлял:

```text
67796480 байт
```

Теперь проверьте манифест.

```bash
cat firmware/yandexmini_2/manifest.json
```

Проверьте платформу и версию. Они должны совпадать полностью.

### Проверка SHA256

Выполните следующую команду.

```bash
sha256sum firmware/yandexmini_2/0.369.1.46.4778262943.20261013.299.zip
```

Ожидаемый SHA256:

```text
192aa9842c77257c4955c9a02cea837f91217d25206d2368815700280ab3c8c3
```

Сверьте всю строку полностью.

### Проверка CRC32

Выполните небольшой скрипт.

```bash
python3 - <<'PY'
import zlib
from pathlib import Path

path = Path(
    "firmware/yandexmini_2/"
    "0.369.1.46.4778262943.20261013.299.zip"
)

crc = 0

with path.open("rb") as file:
    for chunk in iter(
        lambda: file.read(1024 * 1024),
        b""
    ):
        crc = zlib.crc32(chunk, crc)

print(crc & 0xffffffff)
PY
```

Ожидаемый результат:

```text
1524631406
```

Проверьте три значения.

Размер должен совпасть. SHA256 должен совпасть. CRC32 должен совпасть.

Если есть расхождения, остановитесь. Не продолжайте процедуру дальше.

## Подготовка OTA

Теперь разрешим выдачу прошивки.

Сначала создадим рабочие каталоги.

```bash
cd ~/lite-kit
mkdir -p run log
```

Проверьте защитный маркер.

```bash
ls -la run/
```

Нас интересует файл `no_downgrade`.

Он блокирует автоматическую выдачу OTA. При его наличии обновление не предлагается.

### Временно отключаем блокировку

Если файл существует, переименуйте его.

```bash
if [ -f run/no_downgrade ]; then
    mv run/no_downgrade run/no_downgrade.disabled
fi
```

Теперь проверьте результат полностью.

```bash
ls -la run/
```

Файл блокировки теперь отключён. Не удаляйте резервный файл.

### Включаем режим OTA

Установщик подсказывает этот шаг.

```bash
touch run/downgrade
```

Этот флаг включает режим даунгрейда. Скрипт передаст его серверу.

Теперь перезапустим стенд.

```bash
./stop.sh
sudo ./start.sh
```

Если стенд ещё не запускался, можно сразу выполнить запуск.

Проверьте сообщение режима.

В журнале ожидается `[ДАУНГРЕЙД]`. Это подтверждает выбранный режим.

### Что блокирует OTA

Файл `run/no_downgrade` — блокировка. Его наличие запрещает выдачу.

Файл `run/downgrade` включает режим. Это отдельный переключатель проекта.

Не путайте эти два файла. Они выполняют разные задачи.

## Запуск локального стенда

Теперь запускаем DNS и HTTPS.

Сначала остановите старый процесс.

```bash
cd ~/lite-kit
./stop.sh
```

Укажите адрес компьютера. Замените пример своим адресом.

```bash
sudo env LOCAL_IP=192.168.1.250 BIND_IP=192.168.1.250 ./start.sh
```

Здесь указан пример IP. Подставьте свой LAN-адрес.

Если адрес определяется правильно автоматически, можно использовать короткую команду.

```bash
sudo ./start.sh
```

Оставьте это окно открытым. Сервер должен продолжать работать.

### Что запускается

Скрипт поднимает DNS-службу dnsmasq. Она слушает локальный адрес компьютера.

Затем запускается HTTPS-сервер eQuasar. Он использует порты 80 и 443.

Сервер использует сертификаты проекта. Отдельно устанавливать их не нужно.

### Проверка запуска

Скрипт покажет адрес компьютера. Также покажет состояние прошивки.

Проверьте строку с прошивкой. Там должна быть наша версия.

Если сервер сообщает об ошибке, остановитесь. Сначала исправьте причину.

### Проверка DNS

Откройте второе окно терминала.

Подставьте адрес своего компьютера.

```bash
dig +short @192.168.1.250 quasar.yandex.net A
```

Ответ должен совпадать с IP. Это адрес локального компьютера.

Проверьте второй домен.

```bash
dig +short @192.168.1.250 quasar.yandex.ru A
```

Ответ должен быть таким же.

Проверьте третий домен.

```bash
dig +short @192.168.1.250 scbh.yandex.net A
```

Все три домена должны разрешаться локально.

Если ответ пустой, остановитесь. Пока DNS не работает, продолжать нельзя.

### Если DNS не работает

Проверьте адрес компьютера. Проверьте состояние dnsmasq.

Проверьте порт 53. Проверьте файл `run/dnsmasq.conf`.

Покажите его содержимое.

```bash
cat ~/lite-kit/run/dnsmasq.conf
```

Проверьте журнал DNS.

```bash
tail -n 100 ~/lite-kit/log/dnsmasq.log
```

### Особенность DNS в России

В нашем эксперименте менялись DNS-пересылки. Использовались серверы AdGuard DNS.

Это была локальная настройка. Она не обязательна для метода.

Если стандартные DNS доступны, оставьте исходную конфигурацию проекта.

Если пересылки не работают, проверьте доступность DNS-серверов.

Не копируйте чужие настройки автоматически.

## Сброс колонки

Теперь подготовим саму станцию.

Ещё раз проверьте модель. Нужна именно YNDX-00021.

Сброс удалит прежнюю привязку. Колонку придётся настроить заново.

### Последовательность сброса

Сначала отключите питание колонки. Подождите несколько секунд.

Теперь снова подайте питание. Сразу удерживайте кнопку паузы.

Кнопка обозначена символом `▶/⏸`. Удерживайте её примерно 7–10 секунд.

Дождитесь жёлто-салатового индикатора. После этого отпустите кнопку.

Дождитесь приветствия Алисы. Колонка должна завершить сброс.

**Важно:** эта последовательность взята из инструкции проекта lite-kit.

Сверяйте поведение своей ревизии. Не применяйте кнопки другой модели.

## Контроль обновления

Теперь наблюдаем за OTA.

Откройте журнал сервера.

```bash
tail -f ~/lite-kit/log/server.log
```

Следите за новыми строками.

Сначала появятся сетевые проверки. Затем колонка запросит обновление.

### Первый важный маркер

Найдите строку `OTA-AUTO`.

Она показывает выбранную прошивку. Платформа должна быть `yandexmini_2`.

Целевая версия должна совпасть.

```text
0.369.1.46.4778262943.20261013.299
```

В нашем эксперименте колонка сообщала:

```text
0.17.1.32.1145264292.20211203.factory-3.FACTORY.factory
```

Стенд предложил новую версию. Это было видно в `OTA-AUTO`.

### Второй важный маркер

Колонка запросит ZIP-файл.

Путь содержит платформу `yandexmini_2`. Имя файла содержит версию прошивки.

В журнале будет запрос OTA. Затем появится размер передачи.

Ищите такую строку:

```text
[OTA] файл отдан ПОЛНОСТЬЮ (67796480 б)
```

Это подтверждает полную передачу. Файл передан целиком сервером.

### Третий важный маркер

После обновления версия изменится. Колонка снова запросит `check_updates`.

Теперь будет указана новая версия. Стенд ответит `hasUpdate:false`.

Это ожидаемое поведение. Повторно выдавать файл не нужно.

### Не прерывайте OTA

Не отключайте питание колонки. Не выключайте компьютер со стендом.

Не меняйте DNS во время обновления. Не перезапускайте роутер без необходимости.

Дождитесь окончания передачи. Дождитесь следующей синхронизации.

---

## Включение ADB

После OTA начинается следующий этап.

Колонка запрашивает `/get_sync_info`. Это запрос синхронизации настроек.

Стенд получает ответ Яндекса. Затем добавляет параметры ADB.

В нашем тесте исходный ответ не содержал параметров ADB.

Это видно по строке `SYNC-NATIVE`. Значения `adbd` были пустыми.

После обработки появились параметры. Это видно по строке `SYNC-REAL→`.

В журнале были такие отметки:

```text
config.system_config.adbd=on
config.system_config.adbd.network=on
config.device_config.adbd=on
config.adbd=on
top.adbd=on
```

Сервер добавляет параметры в ответ. Он сохраняет остальные поля Яндекса.

В нашем случае ответ был настоящим. Стенд изменил только настройки ADB.

### Что это означает

Станция получила команду включения ADB. Служба должна открыть сетевой порт.

Обычно используется порт 5555. Теперь можно проверить доступность.

---

## Проверка Root

Сначала найдите IP колонки.

Откройте список DHCP-клиентов роутера. Найдите подключённую станцию.

Запишите её локальный IP. Не публикуйте этот адрес открыто.

### Проверка порта

Теперь выполните следующую команду.

```bash
nc -vz -w 5 <IP_КОЛОНКИ> 5555
```

Замените шаблон реальным адресом.

При успехе появится `succeeded`. Это означает доступность порта.

### Подключение через ADB

Теперь выполните подключение.

```bash
adb connect <IP_КОЛОНКИ>:5555
```

Ожидаемый ответ:

```text
connected to <IP_КОЛОНКИ>:5555
```

Проверьте список устройств.

```bash
adb devices
```

Колонка должна иметь статус `device`.

### Главная проверка

Теперь выполните команду.

```bash
adb shell id
```

В нашем тесте получен ответ:

```text
uid=0(root) gid=0(root)
```

Это подтверждает Root-доступ. Команда выполнена от суперпользователя.

**Поздравляем! Доступ Root успешно получен.**

Не путайте ADB и Root. Открытый порт ещё ничего не доказывает.

Root подтверждает именно команда `id`. В выводе должен быть `uid=0`.

## Завершение процедуры

Теперь восстановим защиту OTA.

Верните прежний маркер. Если его не было, создайте новый.

```bash
cd ~/lite-kit

if [ -f run/no_downgrade.disabled ]; then
    mv run/no_downgrade.disabled run/no_downgrade
elif [ -f run/no_downgrade.before-ota ]; then
    mv run/no_downgrade.before-ota run/no_downgrade
else
    touch run/no_downgrade
fi
```

Теперь проверьте саму блокировку.

```bash
test -f run/no_downgrade && echo "OTA LOCK: ON"
```

Ожидаемый результат:

```text
OTA LOCK: ON
```

Теперь отключим режим даунгрейда.

```bash
rm -f run/downgrade
```

Остановите локальный стенд.

```bash
./stop.sh
```

Верните DNS роутера. Выберите автоматическое получение DNS.

Сохраните настройки роутера. Переподключите домашние устройства.

### Что остаётся

ADB может остаться активным. Это зависит от прошивки станции.

Мы не проверяли перезагрузку. Не обещаем постоянный Root.

Не удаляйте рабочие файлы. Сначала убедитесь в результате.

## Если возникли проблемы

Не меняйте всё сразу. Проверяйте этап за этапом.

### Не запускается dnsmasq

Проверьте установку пакета.

```bash
command -v dnsmasq
```

Проверьте конфигурацию DNS.

```bash
sudo dnsmasq --test -C ~/lite-kit/run/dnsmasq.conf
```

Проверьте занятый порт 53.

```bash
sudo ss -lunpt | grep ':53'
```

### Порт 80 или 443 занят

Посмотрите владельца порта.

```bash
sudo ss -lntup | grep -E ':(80|443)\\b'
```

Возможны nginx или Apache. Могут работать другие службы.

Остановите только известную службу. Не отключайте системные службы наугад.

### DNS возвращает неправильный IP

Проверьте локальный адрес компьютера.

```bash
ip -4 addr
```

Проверьте DNS-запрос к стенду.

```bash
dig +short @<IP_КОМПЬЮТЕРА> quasar.yandex.net A
```

Ответ должен быть локальным IP. Проверьте настройки DHCP роутера.

### Колонка не видит интернет

Проверьте, получила ли колонка IP. Не допускайте адреса `169.254.x.x`.

Проверьте журнал DNS. Проверьте журнал сервера.

Проверьте `HEAD /generate_204`. Нормальный ответ — код `204`.

### Не появляется OTA-AUTO

Проверьте наличие прошивки.

```bash
ls -lh firmware/yandexmini_2/
```

Проверьте манифест платформы.

```bash
cat firmware/yandexmini_2/manifest.json
```

Проверьте защитный маркер.

```bash
ls -l run/no_downgrade
```

Если маркер существует, OTA заблокирована намеренно.

Проверьте запрос `check_updates`. В нём должна быть платформа `yandexmini_2`.

### В журнале нет ZIP

Проверьте имя файла. Проверьте папку платформы.

Не переносите архив вручную. Сохраните структуру установщика.

Правильный путь содержит `yandexmini_2`. Внутри лежит ZIP-файл.

### ZIP передался не полностью

Найдите итоговую строку OTA. Сравните переданный размер.

Нужный размер — 67796480 байт. Итог должен совпасть полностью.

Если размер меньше, остановитесь. Не выключайте колонку принудительно.

Сначала проверьте сеть. Затем изучите журнал сервера.

### После OTA порт 5555 закрыт

Проверьте версию колонки. Она должна совпасть с целевой.

Проверьте запрос `get_sync_info`. Найдите отметки `SYNC-REAL→`.

Проверьте значения `adbd`. Они должны иметь состояние `on`.

Подождите завершения синхронизации. Затем повторите проверку порта.

### ADB подключается, Root отсутствует

Сначала проверьте подключение.

```bash
adb devices
```

Затем проверьте пользователя.

```bash
adb shell id
```

Без `uid=0(root)` Root не подтверждён. Не называйте это полноценным Root.

Не запускайте случайные команды. Сначала изучите состояние системы.

### Сервер пишет 429

Это ограничение Яндекса. В нашем тесте оно встречалось.

Стенд повторяет запросы автоматически. По умолчанию выполняются три попытки.

Пауза составляет 2,5 секунды. После этого используется локальный ответ.

Если синхронизация завершилась, единичный 429 не всегда критичен.

### Ошибка TLS или сертификата

Проверьте системное время. Проверьте сертификаты проекта.

Не заменяйте сертификаты случайными файлами. Не отключайте проверку безопасности наугад.

## Безопасность и ограничения

Работайте только со своим устройством. Используйте только свою сеть.

Не публикуйте `sync_real.json`. В нём есть приватные данные.

Не публикуйте device_id колонки. Не публикуйте токены и cookies.

Не публикуйте Wi-Fi-хеши. Не публикуйте приватные ключи.

Не публикуйте полные журналы. Сначала проверьте их содержимое.

Не прошивайте другую модель. Не используйте чужие архивы.

Не отключайте питание во время OTA. Не прерывайте обновление без причины.

### Что мы не делали

Мы не меняли разделы UBI. Мы не записывали данные в /system.

Мы не устанавливали init-скрипты. Мы не изменяли загрузчик.

Мы не проверяли постоянство Root. Эти этапы требуют отдельного исследования.
